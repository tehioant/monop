# Account, sign-in and privacy

Open **Settings → Account**. The app still supports offline solo play and online guests with no provider configured. Play online once to create the guest account before linking it. **Link** adds a provider to that account; **Restore** replaces the local sign-in with the account already linked to the selected provider. Neither operation identifies players by email. **Delete account** asks for confirmation and deletes the online account, not the offline solo save. If the server does not confirm deletion, Account checks whether the same sign-in is still valid. An invalid sign-in is cleared on this device without claiming the account was deleted; if the check is unavailable or the sign-in is still valid, you can retry.

## Configuration

- **App:** set `EXPO_PUBLIC_PRIVACY_POLICY_URL` to the approved HTTPS policy page. If unset or invalid, Account shows the policy as unavailable. Set `EXPO_PUBLIC_SERVER_URL` to the game's `wss://` URL; Account calls the HTTPS `/account` routes on that same origin. The default `ws://` development endpoint still supports guest gameplay but will not receive account credentials over plain HTTP.
- **Server:** set `ACCOUNT_ORIGIN` to the public HTTPS origin of the game server. Register the exact matching callback ending in `/account/callback/google` or `/account/callback/apple`. Do not enable proxy logging of callback query strings, request authorization, bodies, or redirect headers. Server-side secrets are never `EXPO_PUBLIC_*` variables.
- **Google:** set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from a Google OAuth web application. The server exchanges the code and verifies the signed ID token, with PKCE, state, nonce and an `openid` scope.
- **Apple:** set `APPLE_CLIENT_ID` to the Services ID, `APPLE_CLIENT_SECRET` to its signed client-secret JWT (rotate before expiry), and `APPLE_TOKEN_KEY` to a separately managed 32-byte key encoded as unpadded base64url. The server asks for no name or email scopes, verifies the signed ID token, and encrypts the refresh token needed to revoke the Apple authorization on deletion. Keep the encryption key available for as long as its tokens exist; key rotation requires migrating/re-encrypting existing material, not replacing the key in place. Deletion fails rather than skipping Apple revocation when it is unavailable.

Apple revocation material is ordered by the signed ID token's issuance time (`iat`) from the same authorization-code exchange. A later issuance can replace the material; equal, older or missing material leaves it unchanged. Existing bindings keep their encrypted material on migration and accept the first replacement with a verified issuance time; the old material has no recorded order. This ordering does not assume Apple issues a distinct timestamp for every exchange.

Only fully configured providers appear. The native return is `atlas://account-auth`; it carries a short-lived, single-use code that also requires the initiating device's verifier. The production binary needs the `atlas` scheme and Expo web-browser module (a native build, not a web deployment). Configure and verify actual provider return on iOS and Android before release; the fixture tests do not do this.

The current room runtime is single-server: keep account callbacks (including begin and redemption), game sockets and database room writes on that same process. Pending sign-ins and verified results expire automatically, and deletion also clears sign-ins associated with the erased account or its verified provider bindings. Restart discards all in-flight sign-ins. Account deletion revokes all Atlas credentials, removes the bindings, and de-identifies the deleted player's entries in live room seats, snapshots and summaries without deleting other players' game state. A released seat's original owner is retained only in server persistence until erasure. Existing anonymous released-seat display names with no surviving owner are anonymized on startup rather than attributed by name. New lobby bots carry a server-generated marker so startup preserves their names. Older unmarked entries remain subject to anonymization; names already rewritten cannot be recovered from the snapshot. Configure backup and external access-log retention separately; this operation does not rewrite backups or data cached on other devices.
